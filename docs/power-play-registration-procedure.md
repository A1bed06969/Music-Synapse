# ①パワープレイ情報 登録手順

**位置づけ**: [data-registration-guidelines.md](./data-registration-guidelines.md)の優先順位①にあたる作業の具体的な実行手順。自動収集・ファクトチェック・マッチング・本登録の各機能は[radio-power-play-automation設計](./superpowers/specs/2026-09-02-radio-power-play-automation-design.md)で既に実装済みであり、**新規実装は不要**。本ドキュメントはそれらを使って実データを登録するための運用手順(1つずつ確認しながら進める、という原則の実践)を定める。

## 前提

- 対象: `media.media_type='radio'`の局が持つパワープレイ/ヘビーローテーション情報
- 実行環境: ローカル(`supabase start`)固定(本番Supabaseは2026-09-18に復旧断念、ローカル再構築に全面移行済み)。`.env.local`がローカルスタックを向いていることを開始前に確認する
- 使用する既存機能:
  - URL管理: `scripts/backfill-radio-station-urls.ts`(2026-09-02時点で約40局分登録済み。SNSのみ・複数月混在・TLS不備等の理由でこのスクリプトに載せられない局は、コメントに理由付きで明記されている)
  - 収集: `/admin/data/media/radio-power-play-collect`(ボタン1つで全局分をGemini抽出、月内重複は自動スキップ)
  - ファクトチェック: `/admin/data/media/radio-fact-check`
  - マッチング・本登録: `/admin/data/media/radio-airplay-pick`(未マッチ/マッチ済み・未登録/本登録済みの3ビュー)

## 完了条件(着手前にここで確定させる)

> `power_play_url`設定済みの全局について、当月分の「収集→ファクトチェック→マッチング→本登録」が完了し、かつ`radio_airplay_pick`の当月分のうち `fact_checked_correct` が未確定(null)の行が0件、かつ「未マッチ」タブの当月分が0件になったら、①は完了とする。

- URL未設定局(手動運用対象、`STATION_URLS`のコメントに列挙済み)は、従来通りHRPPシート運用の対象として本条件のスコープ外とする
- 「当月」は実行時のJST月を指す。月が変われば同じ手順を繰り返す(月次運用)

## 手順

### Step 1: 収集(自動)

1. `/admin/data/media/radio-power-play-collect`を開き、「今すぐ全局を収集する」を押す(何度押しても安全)
2. 結果画面で局ごとの成功/失敗/新規件数を確認する
3. 取得失敗が目立つ局は、局サイトでURLが変わっていないか確認し、変わっていれば`scripts/backfill-radio-station-urls.ts`を更新して再実行する(月ごとにURLが変わる局(エフエム秋田等)は月初に必ずここを確認する)

### Step 2: ファクトチェック(人力・最重要)

ガイドラインの「事実ベースで登録する」原則を実際に担保する工程。Gemini抽出はこのセッション中にもフィールド入れ替わり・アーカイブ誤抽出等のバグが見つかっているため、必ず1件ずつ目視確認する。

1. `/admin/data/media/radio-fact-check`で対象月を選択する
2. 局ごとに表示された(アーティスト名, 曲名)を、局サイトの実際のページと突き合わせる
3. 正しければ「TRUE」にチェック。誤っていれば「FALSE」にしてその場で正しい値へ修正・保存する(修正値はそのまま後続のマッチングに使われる)
4. **抽出済みの項目が正しいかだけでなく、ページに載っている曲を全て拾えているかも確認する**(ガイドラインのルール9)。1ページに複数コーナー/複数カテゴリー(例: 「POWER PLAY」と「E∞Tracks」の2企画)がある局は特に見落としやすい。抽出0件・件数が少なすぎる局だけでなく、一見正常に見える局も実際のページと突き合わせて確認する
5. **週間周期の局(`utils/radioStationPeriod.ts`の`WEEKLY_STATIONS`。2026-09時点: 秋田放送・TBSラジオ・ベイエフエム・山梨放送)は、自動収集が直近1週分しか拾っていないことがある**。局サイトのバックナンバー/アーカイブページ(例: 山梨放送は`/hits/YYYY/MM/`形式の月別アーカイブがある)を確認し、**その週の開始日が対象月に含まれる週は全て**手動で拾う(1ヶ月に複数週分が存在しうる)
6. 「未抽出」表示の局(自動収集URLがない、または今月0件)は、局サイトを直接確認し「+ 手動で追加」から曲を登録する(Apple Music検索 or URL貼り付け)
7. **当月分の`fact_checked_correct`が全行で確定するまで次のStepに進まない**(nullを残したまま進めない)

### Step 3: マッチング(自動+人力レビュー)

**注意(2026-09-19追記)**: Step1の収集時点で`findItunesCandidate`(単純なiTunes検索)により自動で候補が付くため、このタブの「マッチ済み」に来る行はGeminiのレビューを一度も経ていない。同名異曲(例: 2026年9月に19局で同時にプッシュされていた「tomato」が、無関係な同名異曲に自動マッチしていた実例)を見逃したまま登録してしまった事故があった。人気曲(複数局で同時に登場する曲)ほど同名衝突のリスクが高いという逆説を念頭に置くこと。

1. `/admin/data/media/radio-airplay-pick`(未マッチタブ)を開く
2. 「Geminiで一括マッチング」を実行する。確信度0.9以上は自動反映(自動反映一覧に表示)、それ未満は「要確認キュー」に回る
3. 要確認キューの各候補は、ガイドラインのルール2・10(検索結果を機械的に採用しない、特に人気の高い項目ほど同名異曲/異人を疑う)に従い、アーティスト名の完全一致・国・ジャンルの妥当性を目視確認してから採用/却下する
4. 自動・要確認のいずれでもマッチしなかった残りは、`RadioPickMatcher`で手動検索して候補を設定する
5. **「マッチ済み・未登録」タブも(Step1の自動候補付与だけで来た分がないか)一通り目を通す**。特に複数局に同時に登場する曲名は、局をまたいで候補アーティストが同一かどうか突き合わせると誤マッチに気づきやすい
6. **未マッチタブの当月分が0件になるまで次のStepに進まない**(見つからない場合は次月に持ち越さず、Step2に戻って曲名・アーティスト名の表記揺れを疑う)

### Step 4: 本登録(人力・最終確認)

1. `/admin/data/media/radio-airplay-pick`(マッチ済み・未登録タブ)を開く
2. アートワーク・アーティスト名・曲名を見て、Step3で確認済みの妥当な候補であることを再確認してから「登録」を押す(この操作で未登録のartist/trackは自動作成される)
3. 誤登録に気付いたら「本登録を解除」でいつでも取り消せる(マッチ済み・未登録へ戻る)

### Step 5: 完了確認

上記の完了条件を満たしているか確認する。満たしていれば①は完了とし、②キュレーション情報に進む。

## 既知の制約(現時点でURL自動収集の対象外・要注意な局)

- SNS(X等)のみで公式サイトにページがない: アール・エフ・ラジオ日本、静岡放送、南日本放送、北陸放送 → 手動運用を継続
- 複数月分がアーカイブ形式で1ページに混在し自動切り分けが困難: TBSラジオ、エフエム東京、熊本放送、エフエム岐阜、エフエム京都 → 手動運用を継続
- TLS設定が弱くNode.jsのfetchが拒否する: エフエム徳島 → 手動運用を継続
- JSレンダリング依存でHTML取得のみでは0件になりやすい: ベイエフエム等 → Step2の「+手動で追加」で補う
- URLが月ごとに変わる: エフエム秋田 → 月初にURL更新が必要
